## Wave 1: S-Effort Quick Fixes

These 3 confirmed-open S-effort items can each be implemented in under 2 hours. Run all three in parallel.

### G-034: GPG Signature Verification

**Status:** Open. `gpgFingerprint` field stored in DB, accepted in manifest, but never verified against downloaded bundle content.

**Decision:** Implement full GPG verification using the `openpgp` npm package rather than removing the field. Removing it is a downgrade — operators who configure signed plugins expect enforcement. The field is already in the DB schema, manifest schema, and tests.

**Files to modify:**
- `services/plugin/src/services/plugin-service.ts` — add `verifyGpgSignature(bundle, fingerprint)` call after bundle download, before checksum verification
- `services/plugin/src/schemas/index.ts` — add `gpgSignatureUrl` optional field alongside `gpgFingerprint` (the detached `.asc` file URL)

**Files to create:**
- `services/plugin/src/utils/gpg-verify.ts` — wraps `openpgp.verify()`, accepts bundle bytes + detached signature bytes + expected fingerprint, returns `{valid: boolean, signer?: string}`

**API contract change:** `POST /api/v1/plugins` — if `gpgFingerprint` is present in the manifest, `gpgSignatureUrl` is now required. Return `422` with `code: MISSING_GPG_SIGNATURE_URL` if absent.

**Tests needed:** 5 unit tests in `services/plugin/src/__tests__/gpg-verify.test.ts` (valid sig, wrong key, corrupted bundle, missing sig, no fingerprint = skip), plus 3 integration test cases in existing plugin-service tests.

### G-126: Sandbox V8 Hardening Flags

**Status:** Open. Execution service uses `isolated-vm` for JS/TS execution but does not pass V8 hardening flags.

**Files to modify:**
- `services/execution/src/services/execution-engine.ts` (or wherever `new ivm.Isolate()` is called) — add `flags: ['--disallow-code-generation-from-strings', '--jitless']` to the isolate options

**Note:** `--jitless` reduces performance by 15-30% for compute-heavy scripts but is the correct security posture for untrusted tenant code. Document this tradeoff in a comment. Operators who need maximum throughput should run dedicated execution clusters without `--jitless`.

**Tests needed:** 2 tests verifying that `eval()` and `new Function()` throw inside the isolate; 1 test verifying normal code still executes correctly.

### G-133: Auto-Generated Docs Pipeline

**Files to modify:**

### G-120: GDPR Data Subject Request Tools

**What:** No GDPR tooling. No right-to-access, right-to-deletion, or data export. Required for any EU deployment.

**Approach:** This is a cross-service coordination feature. Implement as a new route group on the Gateway (the only service that has authority over all tenant data):

**Data Subject Request API:**
- `POST /api/v1/gdpr/access-requests` — body `{subjectEmail}`. Creates a request, queues a job to collect all data for that email across: auth (user record, sessions, audit log), ingestion (raw table rows where user identifiable), logging (log entries), app (app storage items).
- `GET /api/v1/gdpr/access-requests/:id` — poll status. When complete, returns a signed download URL to a JSON export.
- `POST /api/v1/gdpr/deletion-requests` — body `{subjectEmail, confirm: true}`. Queues deletion across all services. Auth user is deactivated. Raw table rows with that email are nulled/deleted. Audit log entries are anonymized (email replaced with `[DELETED]`). Returns a deletion receipt.
- `GET /api/v1/gdpr/deletion-requests/:id` — poll status and completion certificate.

**Implementation strategy:**
- New BullMQ queue `gdpr:access` and `gdpr:deletion` in the Gateway service (or a dedicated lightweight service if scope warrants)
- Each service exposes an `/internal/gdpr/export/:email` and `/internal/gdpr/delete/:email` endpoint on its existing internal router
- The Gateway orchestrates: calls each service's internal endpoint, collects results, writes to MinIO for access requests

**Files to create:** `services/gateway/src/routes/gdpr.ts`, `services/gateway/src/services/gdpr-orchestrator.ts`, `services/gateway/src/jobs/gdpr-worker.ts`

**Files to modify:** All 9 service `internal.ts` routes (add GDPR endpoints), `services/gateway/src/routes/index.ts`

**Tests needed:** 15 unit tests (access request creation, deletion request, orchestrator logic, each service's internal endpoint, anonymization), 2 integration tests (full access request cycle, full deletion cycle)

### G-085: Asymmetric JWT Signing (RS256/EdDSA)

**What:** `services/auth/src/services/token-service.ts` line 1 has a `TODO` noting HS256 should be migrated to RS256/EdDSA. A single compromised `JWT_SECRET` breaks all token verification across all services.

**Approach:** Migrate to EdDSA (Ed25519) — consistent with the existing service-to-service key infrastructure already using Ed25519 (G-005 was fixed in P1). Avoids having two different asymmetric algorithms in the stack.

**Migration steps (must be zero-downtime):**
1. Add `JWT_PRIVATE_KEY` and `JWT_PUBLIC_KEY` to `.env.example` (PEM format, generated by `init.sh`)
2. Modify `services/auth/src/services/token-service.ts`: sign with EdDSA using `JWT_PRIVATE_KEY`
3. Modify `packages/core/src/middleware/auth.ts`: accept tokens signed by either EdDSA `JWT_PUBLIC_KEY` or the legacy `JWT_SECRET` (HS256) during a transition window. Add `JWT_LEGACY_SECRET` env var for transition.
4. `docker/init.sh` — generate Ed25519 key pair using `openssl genpkey` + `openssl pkey`, write to `.keys/jwt-private.pem` and `.keys/jwt-public.pem`, mount into containers as read-only volumes
5. After all running tokens have expired (24-hour window), remove HS256 support from auth middleware

**Risk:** All services must have access to `JWT_PUBLIC_KEY` for verification. This is mounted via Docker Compose volume — already the pattern for service Ed25519 keys.

**Files to modify:** `services/auth/src/services/token-service.ts`, `packages/core/src/middleware/auth.ts`, `docker/init.sh`, `docker/docker-compose.yml`, `.env.example`

**Tests needed:** 8 unit tests (sign with EdDSA, verify EdDSA token, reject tampered token, HS256 token rejected after transition, HS256 token accepted during transition window)

### G-044: Schema Drift Detection

**Architectural approach:** After every connector sync completes, compare the fetched records' field set against the stored entity schema in the Ontology Service. Differences trigger an `ingestion.schema.drift.detected` event.

**Component breakdown:**
1. `services/ingestion/src/utils/schema-differ.ts` — pure function: given `{expected: Record<string, FieldType>, observed: Record<string, unknown>[]}`, returns `{added: string[], removed: string[], typeChanged: {field, from, to}[]}`. Samples first 100 records to infer types.
2. Modify sync job worker — after fetching records, call `schemaDiffer()`. If drift detected, emit event via `packages/core/src/events/` and write a `schema_drift_events` record to Postgres.
3. `services/ingestion/src/db/migrations/003_schema_drift.sql` — `(id, connector_id, detected_at, drift_json, acknowledged_at)`
4. `GET /api/v1/connectors/:id/schema-drift` — returns unacknowledged drift events

### G-057: Conditional Branching in Pipelines

**Dependency:** G-056 (DAG schema required)

**Architectural approach:** A "Condition" node in the pipeline DAG. The node has a JSONata expression (already used elsewhere for evaluation) and two outbound edges: `trueBranchId` and `falseBranchId`. During execution, the engine evaluates the expression against the current pipeline context, then follows the appropriate edge.

**Schema extension:**
```typescript
interface ConditionStep extends PipelineStep {
  type: 'condition';
  expression: string; // JSONata
  trueBranchId: string;
  falseBranchId: string;
}
```

**Execution engine:** After completing a step, check if the next step has incoming condition edges. If so, evaluate the condition and select the branch. Already have `evaluateWithTimeout()` from JSONata work.

**Frontend:** "Condition" node type in React Flow canvas with a diamond visual. Two output handles (true/false). Property panel shows expression editor with a test input field.

**Tests needed:** 15 tests (condition evaluation, true branch taken, false branch taken, nested conditions, expression timeout handled)

## P3 Gaps: Competitive Differentiation (25 items)

### G-045: Change Data Capture (CDC)

**Description:** Database sources (PostgreSQL, MySQL connectors) currently only support full sync and cursor-based incremental. CDC via WAL (PostgreSQL) or binlog (MySQL) would deliver sub-second data freshness.

**Approach:** Implement as a new connector plugin type `cdc-connector` (distinct from `connector`). A CDC connector runs a long-lived process subscribing to the source database's replication stream. For PostgreSQL: use `pg_logical` protocol via `pg_recvlogical` or the `wal2json` plugin. For MySQL: binlog protocol via `mysql-binlog` npm package. The CDC worker process lives in a new BullMQ worker type `cdc-worker` that maintains a persistent connection rather than a periodic job.

**Files to create:** `plugins/connector-postgres-cdc/`, `plugins/connector-mysql-cdc/`, new BullMQ worker type in ingestion service

**Effort:** XL (3-5 days). Do not start until G-055 (durable sync history) is complete — CDC events must be durably recorded.

### G-046: Data Lineage Tracking

**Description:** No way to trace a record from its destination table back to its source connector.

**Approach:** Add `lineage_metadata: {sourceConnectorId, sourceRecordId, syncRunId, mappingRuleIds[]}` JSONB column to all ontology entity tables (or a separate `ontology.lineage` table for performance). Populate during the mapping step. Frontend: `LineagePage.tsx` showing a DAG visualization (source -> raw -> mapped -> pipeline -> app) using `@xyflow/react` (already added for G-056).

**Effort:** L (2-3 days).

### G-051: SQL-Based Transformation Library

**Description:** Only raw JS/TS expression transforms in mapping rules. SQL-based transformations (GROUP BY, JOIN, aggregates) would make OnePlatform useful for analytics use cases.

**Approach:** New `TransformationPipeline` entity in the Ontology Service. A transformation is a SQL SELECT statement (read-only) executed against the tenant's mapped entity tables using a read-only Postgres role. The sandbox execution service can host the SQL execution worker. Return type: a new `derived_entity` type in the ontology.

**Effort:** XL (3-5 days). Requires careful Postgres row-level security to prevent cross-tenant data access.

### G-052: Data Reconciliation

**Description:** No way to compare source data vs platform data for drift detection post-sync.

**Approach:** A reconciliation job that re-fetches source data (via the connector's fetch hook) and compares against the stored raw table using a hash-based comparison. Differences written to `ingestion.reconciliation_reports`. Triggered manually or on a schedule.

**Effort:** L (1-2 days).

## P4 Gaps: Long-Horizon Features (8 items)

These are post-enterprise-launch roadmap items. Each requires significant infrastructure or architectural work beyond Phase 14's scope. Brief specification and pre-conditions.

### G-048: Usage Metering and Billing Integration

**Description:** Track rows synced, API calls, storage per tenant. Expose a billing webhook for SaaS operators.

**Approach:** A new `metering` schema in Postgres: `(tenant_id, metric_type, period_start, period_end, value, unit)`. Ingestion service writes meter records after each sync. New `GET /api/v1/admin/metering/:tenantId` route. Billing webhook fired at end of billing period (configurable). Integration with Stripe Billing or Lago (open-source metering).

**Pre-conditions:** G-117 (tenant management API) must be complete. Stripe or Lago integration requires operator credentials and is opt-in.

### G-070: Mobile App Support

**Description:** React Native SDK or PWA with mobile-optimized components.

**Approach:** PWA first (lower risk): add a `manifest.json` and service worker to the frontend, test on mobile browsers. React Native SDK is a separate package `@oneplatform/rn-sdk` wrapping the existing SDK with React Native-specific auth (using SecureStore instead of httpOnly cookies) and mobile-optimized components.

**Pre-conditions:** Requires dedicated UX design work for mobile layouts. Not started until the core web experience is stable.

### G-078: GraphQL API

**Description:** REST-only. No GraphQL.

**Approach:** GraphQL gateway layer auto-generated from ontology schemas. Use `graphql-yoga` or `pothos-graphql`. The schema is dynamically generated from ontology entity definitions. Resolvers map to existing REST API methods. This can be a Gateway plugin (per ADR-34 which defines the plugin gateway extension point).

**Pre-conditions:** Ontology schema registry must be stable. Not started until all ontology-related P2 gaps are closed.

### G-079: gRPC Support

**Description:** HTTP REST only. No gRPC.

**Approach:** gRPC for service-to-service (not external) using `@grpc/grpc-js`. Define proto files in `proto/`. Priority services: ingestion worker, pipeline execution. External gRPC is lower value given REST+GraphQL coverage.

**Pre-conditions:** Requires proto toolchain, code generation pipeline. Significant maintenance overhead. Evaluate demand before investing.

### G-081: Streaming/Real-Time Data Ingestion

**Description:** Kafka, NATS, MQTT inbound streaming.

**Approach:** New `streaming-worker` process type in the Ingestion Service. Each streaming connector maintains a persistent consumer. Events are processed in micro-batches (every 100ms or 1000 records, whichever comes first) through the standard mapping pipeline. Requires Kafka or NATS as external infrastructure.

**Pre-conditions:** G-045 (CDC) must be complete first — the streaming worker architecture is similar. Requires Kafka/NATS in Docker Compose for development.

### G-121: Data Residency Controls

**Description:** Per-tenant data residency configuration, region-aware routing.

**Approach:** This is a fundamental infrastructure change requiring multi-region Postgres deployment, region-aware connection routing at the Gateway, and per-tenant region assignments. Depends on cloud provider infrastructure outside the scope of the Docker Compose stack. Design an ADR before implementation.

**Pre-conditions:** Kubernetes deployment (G-111) must be complete. Requires cloud provider (AWS/GCP/Azure) commitment.

### G-123: White-Labeling / Custom Branding

**Description:** Configurable logo, colors, email templates per tenant.

**Approach:** New `branding` table: `(tenant_id, logo_url, primary_color, email_header_html)`. Branding config served at `GET /api/v1/branding` (public, no auth). Frontend reads branding on app load and applies CSS custom properties. Email templates use Handlebars with branding variables.

**Pre-conditions:** G-117 (tenant management). Relatively low-risk implementation.

### G-124: Multi-Region Support

**Description:** Multi-region deployment with data replication.

**Approach:** This requires a full architectural ADR. Consider: active-active (complex consistency) vs active-passive (simpler, higher RTO). PostgreSQL logical replication or Citus for horizontal sharding. Region-aware CDN for static assets. Cross-region event bus.

**Pre-conditions:** G-121 (data residency). Major infrastructure investment. Not a Phase 14 item.

### Risk Register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| React Flow bundle size makes pipeline page slow | High | Medium | Lazy-load FlowCanvas with `React.lazy()`. Monitor bundle with `vite-bundle-analyzer`. |
| JWT algorithm migration causes auth failures during cutover | Medium | High | Implement transition window accepting both HS256 (legacy) and EdDSA (new). Roll out in off-peak hours. |
| GDPR deletion cascade breaks foreign key constraints | Medium | High | Use soft-delete pattern (null/anonymize) rather than hard DELETE on FKed rows. |
